What verification proves — and what it doesn't

✓
Cryptographic authenticity
The TLSNotary presentation proves a specific HTTPS exchange occurred with the fixture server, with only the disclosed fields revealed.
✓
Storage integrity
Artifact SHA-256 hashes are bound into the evidence record; any tampering breaks the commitment.
✗
Not proven: response truthfulness
Verification proves the bytes came from the server — not that the API's answer was correct.
✗
Not implemented: external timestamping
Hedera anchoring is planned, not live. The commitment is locally computed only.

Documentation

What TRACESEAL is, how verification works, and how to use this console and CLI.

01What TRACESEAL is

TRACESEAL is a local-first system that converts a live HTTPS response into cryptographically verifiable evidence. It uses TLSNotary MPC-TLS: a prover and a notary jointly produce an attestation of a TLS session, and a presentation selectively discloses only chosen response fields.

02The problem it solves

APIs can claim anything in a response. TRACESEAL produces a proof that a specific HTTPS exchange happened with a specific server, revealing only the fields you choose — enabling audit trails, compliance evidence, and dispute resolution without exposing full transcripts.

03How TLSNotary verification works

  1. Prove — traceseal-core prove connects to the fixture over MPC-TLS, requests a URL, and builds a presentation disclosing selected JSON fields.
  2. Verify — a separate traceseal-core verify process checks the attestation signature (pinned demo key), the presentation binding, the server name, and the disclosed transcript.
  3. Identify — the engine cross-checks the verifier's report against the request manifest and artifact hashes, then derives a canonical commitment.

06Evidence ID and commitment

The evidence ID is ts1_ + the first 64 hex chars of a SHA-256 over a domain-separated canonical payload (TRACESEAL:EVIDENCE:V1\0 prefix, RFC 8785 JCS canonicalization). The commitment is the same hash prefixed sha256:. Both are deterministic: identical verified evidence always produces the same ID, and duplicate submissions return already_present.

09Trust model

  • Demo attestor key — a fixed public test key signs attestations. Anyone can forge attestations with it; it is not production trust.
  • Pinned verifier — verification runs the same traceseal-core binary via verify, with TLSNotary v0.1.0-alpha.15.
  • Loopback only — the API binds 127.0.0.1 by default; non-loopback binding prints a warning and has no authentication.
  • Fixture-only endpoints — only https://localhost:4443/trace-seal-{503,200,404,delay} are accepted.

10Limitations

  • Single-user local deployment — no authentication, no multi-user ownership.
  • No global evidence listing endpoint — lookup requires the ts1_ ID.
  • Verification proves the HTTPS exchange occurred, not that the response content was truthful.
  • No external timestamping or anchoring yet.
  • Verifier concurrency is limited (default 4); excess submissions get CONCURRENCY_LIMIT_REACHED.

11Future: Hedera integration

Planned: anchor the evidence commitment to Hedera HCS so the commitment is timestamped by a public ledger. Requires HBAR-funded operator credentials, a topic ID, and mirror-node lookup for comparison. Not implemented — no testnet transactions exist yet.
